How /sys/action reads an action that is still running

The uncommitted change moves the action out of a tokio task local and into the future itself, at a fixed address, so a diagnostic request can find it and copy its trace. That needs raw pointers, a hand-rolled lock and unsafe. This page walks through each piece and what it cost.

The idea in one screen

An action only produces its record when it finishes. A stuck one never finishes, so it was invisible.

Before

tokio task_local!

The Action is a value that tokio moves: on every poll it is swapped from the future into the worker's thread local, and swapped back when the poll returns.

All safe code, nothing shared. But the action has no stable address and no list of live actions exists, so nothing outside the task can look at it.

After

ActionCell + registry

The Action stays inside the pinned future. The thread local holds only a pointer to it during a poll. A global registry holds the same pointer for as long as the action is in flight.

A dump follows the registry pointer and copies the trace. One atomic byte decides whether the worker or the dump may touch the action right now.

Three things keep the dump from reading freed or half-written memory. Keep them in mind, every unsafe block below leans on one of them:
1. Pinning — the cell cannot move, so its address stays valid. 2. The shard lock — a cell removes itself from the registry under the lock before it dies, so a listed pointer is alive. 3. The state byte — IDLE / POLLING / DUMPING, whoever holds it owns the action's contents.

What is inside an ActionCell

        
The struct is split by who may touch each field. This split is the whole safety argument.

        

            
id: [u8; 24], id_len, kind, start_timeAnyone, any time.
                    Copied out of the action once in new, never written again. This is why a dump can print
                    state=running for an action that is being mutated right now.

            
state: AtomicU8Anyone, atomically. The lock.
                    IDLE, POLLING or DUMPING.

            
slot: Cell<Option<(u32, u32)>>Owner only. Which
                    registry shard and index this cell sits in. A plain Cell, the dump never reads
                    it.

            
inner: UnsafeCell<Inner>Whoever holds
                        state. The Option<RefCell<Action>>,
                    AllocStats, PollStats. Compiler checks are off here, every access is an
                    unsafe block.

            
_pinned: PhantomPinnedZero bytes. Makes the type
                    !Unpin, so once pinned it can never be moved by safe code.

        

        
Two layers of interior mutability are stacked on purpose. UnsafeCell plus the state byte
            arbitrates between threads (worker vs dump). The RefCell inside it arbitrates
            between call sites on the same thread (a log! inside a Display impl
            inside another log!), exactly as it did before the change.

The two sides are not symmetric

                
The worker must get in, so it spins until it does. It only ever waits for one trace to be
                    copied, at most about 512KB.

                
The dump must never wait on a worker: a stuck action might hold POLLING for
                    ever (blocking call, deadlock). So it tries three times, yields in between, then gives up and prints
                    state=running from the immutable fields. This is also what prevents a deadlock between
                    the
                    shard lock (held by the dump) and the state byte.
                

            

            

        


        
Why the code has this shape

        
Four of the less obvious pieces each answer a finding in
            plan/action_in_flight_review.md.

        

            
P1 · undefined behaviour
                
Reading a running action

                
The first version printed id and kind by reading the Action while a worker held
                    &mut Action inside log!. Reading through an exclusive borrow is UB
                    even if the
                    bytes read are not the ones written.
                

                
Now: id, kind and start time are copied into the cell's own immutable fields. The running
                    branch never touches inner.

            

            
P1 · wrong behaviour
                
Dropping the task outside its action

                
If a parent times out a child, the child future is dropped while the parent is the
                    current action. A Span the child held would log its elapsed time into the parent.
                    Tokio's
                    wrapper used to prevent this.

                
Now: task is an Option<F>. It is set to None
                    inside
                    cell.poll on completion, and inside cell.enter from
                    PinnedDrop on
                    cancellation, so its destructors always run with their own action current.
                

            

            
P2 · memory
                
One dump could hold every trace

                
1,000 stuck actions × 512KB of trace, copied into one string, then copied again by masking.

                
Now: dump() only lists (pointer, shard, index, start_time). It
                    returns an Iterator, and the new Body::Chunks pulls one action per chunk
                    as
                    the socket is ready. One trace is in memory at a time.

            

            
P2 · latency
                
A shard locked across all its traces

                
Starting and finishing an action take the shard lock, so they waited for the whole scan.

                
Now: the lock is taken per trace. Because it is released between entries, each entry is
                    re-validated: is that slot still holding the same pointer, with the same start time? If
                    not,
                    the action finished meanwhile and is skipped.

The thread dump, briefly

        
/sys/thread is the other half: a running action shows no trace, its
            stack is here, matched by action id.

        
Rust cannot walk another thread's stack from inside the process. So the dump sends each thread a
            signal, and the thread walks its own stack inside the signal handler. A handler runs on top of
            whatever the thread was doing, possibly while it holds the allocator's lock, so it may not allocate or
            lock: it writes raw numbers into preallocated atomics.

This is where the two features meet: the handler calls
            inflight::copy_current_id, which
            reads the same CURRENT pointer log! uses, and only the immutable id bytes behind
            it.
            That is safe mid-poll for the same reason the running branch is.

My read

        
    
            
  • The trade is fair for a framework whose point is always-on observability: the hot path
                (log!) is unchanged and the new cost is per action and per poll.
    • 
            
  • The real price is the unsafe code. It is small and the invariants are clear, but it is the kind that
                stays correct only if every future edit respects them. Miri passes today (see the unsafe audit), running
                it in CI would keep those comments checked.
    • 
            
  • The spin while a 512KB trace is copied is the one place a healthy request can be delayed by a diagnostic
                one. Acceptable for a manual, local-only endpoint, worth knowing before anyone scrapes it on a timer.
            
    • 
            
  • The benchmark comparison with the old task local is still missing, so "likely even" in the table is
                reasoning, not data.
    •
