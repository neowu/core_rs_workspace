Why this can’t be a real main

main returns (). An async fn returns a future. #[tokio::main] rewrites it into a synchronous main that builds a runtime and hands it that future to poll.

Everything async in this repo bottoms out in that one call.

Why is sequential 100 ms?

Because .await means “poll this until it is Ready before continuing”. It is as sequential as any blocking call. async alone buys you nothing — concurrency appears only when something polls more than one future.

Note the interleaving

d and e both start, then e finishes first. join! polls its branches in a loop in one task — no parallelism, just interleaving at .await points. tokio::spawn is the one that may use different threads.

§2.3 — the centre of the session · do not skip

Drive a future by hand, with no runtime at all

struct Countdown { remaining: u32 }

impl Future for Countdown {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        println!("  poll, remaining={}", self.remaining);
        if self.remaining == 0 {
            return Poll::Ready("liftoff");
        }
        self.remaining -= 1;
        cx.waker().wake_by_ref();   // "I could make progress again immediately"
        Poll::Pending
    }
}
let mut future = pin!(Countdown { remaining: 2 });
let mut cx = Context::from_waker(Waker::noop());
loop {
    match future.as_mut().poll(&mut cx) {
        Poll::Pending      => println!("  got Pending, loop again"),
        Poll::Ready(value) => { println!("  got Ready({value})"); break; }
    }
}
your hand-rolled executor
remaining = 2
2

What you just wrote is a runtime — for one future, with a busy-wait instead of a ready queue. Tokio is this loop plus a work-stealing scheduler, an epoll/kqueue driver, and a timer wheel.

the whole thing

Five lines. Everything else is built on them.

pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum Poll<T> { Ready(T), Pending }

async fn, .await, join!, select!, tokio itself — all of it sits on top of that. Four points, one per question the group will ask:

cx: &mut Context

Its only job is to carry a Waker. Returning Pending without arranging for the waker to be called is how a future hangs forever. Countdown cheats and wakes itself; a real leaf future hands the waker to the OS event source.

a Waker is not “resume this coroutine”

It is “put the task that owns this future back on the ready queue”, which re-polls the whole future tree from the top. That is why poll must be cheap and re-entrant.

Poll::Pending is a return, not a yield

The stack is gone. Anything the body needs after the await must have been saved into the future’s own memory. That is the entire reason the next section exists.

self: Pin<&mut Self>, not &mut Self

Nobody has explained this yet. Write “why Pin?” on the board and point at it — it gets answered at 0:45.

0:28 — §3.1 the desugaring

Every local live across an .await becomes a field

Click a line on the left to see where it lands on the right.

what you write
async fn two_step() -> u32 {
    let total = 40;                 // local, before the await
    sleep(20.ms()).await;           // suspension point
    total + 2                      // still needed after the await
}

▸ click a highlighted line.

what the compiler builds
enum TwoStep {
    Start,
    WaitingOnSleep { sleeping: Sleep, total: u32 },
    Done,
}

The rule. Every local that is live across an .await becomes a field of the state machine. Every .await becomes a state. Locals that do not cross an await stay ordinary stack variables inside poll and cost nothing.

This is why a future’s size is what it is: the maximum set of simultaneously-live cross-await locals, plus the awaited sub-futures, plus a discriminant.

§3.2 — write the machine out by hand

Step the machine. Watch WaitingFirst get polled twice.

fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
    let this = self.get_mut();
    loop {
        match &mut this.state {
            TwoStepState::Start => {
                let total = 40;
                this.state = TwoStepState::WaitingFirst(
                    Box::pin(sleep(Duration::from_millis(20))), total);
                // loop round: fall straight into the next state
            }
            TwoStepState::WaitingFirst(sleeping, total) => {
                let total = *total;
                match sleeping.as_mut().poll(cx) {
                    Poll::Pending  => return Poll::Pending,
                    Poll::Ready(()) => {
                        this.state = TwoStepState::Done;
                        return Poll::Ready(total + 2);
                    }
                }
            }
            TwoStepState::Done => panic!("polled after completion"),
        }
    }
}

First poll registers the timer and returns Pending. The timer fires, wakes the task, tokio polls from the top, the match lands back in WaitingFirst, and now Sleep is Ready. There is no “continue where the CPU left off”.

total is in the variant

It was a local. It crossed an await. It became a field. That is §3.1’s rule, made concrete.

why Box::pin the inner Sleep?

Sleep::poll needs Pin<&mut Sleep>. From a field you either heap-pin it (honest, wasteful) or project the outer pin into it — which is what the compiler does, free, and what makes the machine self-referential. Next slide.

0:45 — §4.1 / §4.2 the problem

Move the bytes. Watch the pointer lie.

async fn borrows_across_await() {
    let owned = String::from("hello");
    let borrowed: &str = &owned;   // a reference into this future's OWN memory
    yield_now().await;
    println!("{borrowed} {}", owned.len());
}

Both live across the await, so both become fields — and one points at the other. size_of_val says 64 bytes, containing a pointer to one of its own fields.

The invariant. Once a self-referential future has been polled even once, it must never move again.

Lifetimes cannot express that — the borrow is inside a single value, and the struct is generated, not written. So the guarantee moves into the type of the poll receiver.

Rust moves are memcpy of the bytes and nothing else. No move constructor, no relocation hook, no way for a type to say “fix up my interior pointers”.

Dereferencing b.pointer after the move would probably still print 1 — the old stack slot isn’t overwritten yet. That is the worst outcome: silent, intermittent UB that survives testing. Demo the boolean, never the dereference.

§4.3 — everyone mis-models this at first

What Pin actually is

Pin<P> is a wrapper around a pointer P that refuses to hand out a &mut to its target, unless the target is Unpin. That is all. It has no runtime representation and pins nothing by itself — it is a promise, enforced by the absence of an API, that the pointee will not move before it is dropped.

Four myths. Click to flip.

myth

“Pin pins memory to an address.”

reality

It removes the only safe way to move the value: &mut T. Without &mut T there is no mem::swap, no mem::replace, no assignment.

myth

“Pin<T>”

reality

There is no such thing. It is always Pin<&mut T>, Pin<Box<T>> — a pinned pointer.

myth

“Pin costs something.”

reality

Zero. It is a newtype over the pointer, erased at codegen.

myth

“I need Pin for my types.”

reality

Almost certainly not. Everything you write by hand is Unpin unless it contains PhantomPinned or a coroutine — and Pin<&mut T> where T: Unpin is just a &mut T with extra syntax.

Unpin is the escape hatch, and it is an auto trait. T: Unpin means “moving this is fine even after pinning” — true for u64, String, Vec<T> and every struct you have written so far. It is not true for async fn futures.

get_mut is gated on Unpin; mem::swap needs &mut; therefore the value cannot be swapped out from under its own interior pointer.

pin!(value)

current stack frame · free · when you poll it in this scope. This is what .await does for you.

Box::pin(value)

heap · one allocation · when the future must outlive the frame, live in a collection, or be type-erased as Pin<Box<dyn Future>>.

Pin::new(&mut value)

anywhere · free · only when T: Unpin. Which futures never are.

Where does .await do this? In the desugaring. expr.await pins expr in the enclosing coroutine’s frame and polls it there. You have been pinning futures all along — today is just the first time you had to type it.

1:00 — §5 the framework exhibit

ActionFuture — everything so far was scaffolding for this

lib/framework/src/log.rs:86 · read alongside doc/action_future_design.md. Click the highlighted parts.

pin_project! {
    /// Hand written so the task is stored exactly once.
    pub struct ActionFuture<F> {
        #[pin]
        inner: TaskLocalFuture<RefCell<Action>, F>,
    }
}

pub fn action<F: Future>(kind: &'static str, ref_ids: Option<Vec<String>>, task: F)
    -> ActionFuture<F> {
    let now = DateTime::now();
    let id  = id_generator::next_id(now.unix_timestamp_millis());
    ActionFuture { inner: CURRENT_ACTION.scope(RefCell::new(Action::new(id, kind, ref_ids, now)), task) }
}

impl<F, R> Future for ActionFuture<F>
where F: Future<Output = Result<R, Exception>> {
    type Output = F::Output;

    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        let mut this   = self.project();
        let result     = ready!(this.inner.as_mut().poll(cx));

        let mut current_action = this.inner.take_value()
            .map(RefCell::into_inner).expect("current action must be within the scope");

        if let Err(e) = &result { current_action.log_exception(e); }
        current_action.finish();

        if let Some(sender) = SENDER.get() {
            let _result = sender.send(Message::Action(current_action.into()));
        }

        Poll::Ready(result)
    }
}
what it is

log::action(kind, ref_ids, task) wraps any future so that an Action (id, kind, context, stats, log buffer) is a task-local for that future’s lifetime, and is emitted to the appender the moment the future resolves.

the mechanism, from the design doc

rustc keeps parameters and upvars in the coroutine layout prefix — always live, never overlapped with variant fields. Only ordinary locals get liveness-based slot reuse.

So an async fn log::action(.., task: F) held task three times over:

1

in the outer async fn’s prefix, as a parameter;

2

in the inner CURRENT_ACTION.scope(.., async move { .. }) block’s prefix, as an upvar;

3

in __awaitee, the into_future(task) temporary held across the yield.

Every action future contains its caller’s future, so this is a multiplier, not an overhead. clippy::large_futures denies futures over 16 KB and warnings = "deny" is set — a 6 KB jetstream setup task became 18,032 B and failed the build.

The caller-side rule — the one thing from §5 to remember when you write handlers in Phase 3: never wrap log::action in an async fn. A function whose only job is to .await a log::action(..) must be a plain fn returning impl Future, or it re-adds the 2x on top.

1:10 — lab exercise B

Cancellation is a drop

struct Guard(&'static str);
impl Drop for Guard {
    fn drop(&mut self) { println!("  Guard({}) dropped", self.0); }
}

async fn slow() {
    let _guard = Guard("slow");
    println!("  slow: started");
    sleep(Duration::from_secs(10)).await;
    println!("  slow: finished (never printed)");
}

let result = timeout(Duration::from_millis(100), slow()).await;
slow()
timeout
050100 ms…10 s

Where exactly did slow stop? At the .await. Nowhere else. A future can only be cancelled at a suspension point, because that is the only moment control is outside poll.

the follow-up that matters for Phase 3

If that had been a database transaction between two awaits — what state is the database in? This is why ActionFuture deliberately does not emit an action for a cancelled task: “a dropped, incomplete action is still not emitted”.

select! makes the same point from the other side

The losing branch’s future is dropped where it stood. Anything it was holding — a connection, a permit, a half-written batch — is released by Drop, at that exact .await. That is the mechanism behind the appender drain loop and every CancellationToken in the codebase. Session 8.

1:25 — wrap

The five sentences

If nothing else survives the week, these do.

1

An async fn returns an inert state machine; nothing runs until something polls it.

2

poll returns Ready or Pending, and Pending is a promise that the Waker will be called.

3

Locals that live across an .await become fields of the machine; that is where a future’s size comes from.

4

Those fields can point at each other, so the machine must not move after its first poll — enforced by poll taking Pin<&mut Self> and Pin withholding &mut.

5

A wrapper future stores its inner future in a prefix slot that is never reused, so wrapping with async fn multiplies size — which is why ActionFuture is hand-written.

pitfalls · error decoder · parked list

What will actually bite you in Phase 3

pitfalls to state explicitly
!

Blocking in async

No std::thread::sleep, no blocking file I/O, no CPU-bound loops on a runtime thread. A worker inside poll cannot poll anything else. Use tokio::time::sleep, tokio I/O, or spawn_blocking.

!

Holding a std::sync::MutexGuard across .await

Doesn’t compile. The guard became a field of the future (§3.1’s rule) and tokio::spawn needs Send. Fix: end the borrow before the await. The rest is Session 7.

!

Assuming an async block starts on creation

Bites hardest with metrics guards and timers, which then measure the wrong thing.

!

Bare tokio::spawn for app work

Use spawn_action! — it registers with the TaskTracker and links the child action to the parent by ref_id. Session 8.

!

Deep async fn wrapper chains

Every layer that owns a future adds a copy of it. Watch large_futures.
